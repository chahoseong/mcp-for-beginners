## Simple Auth 수업 계획

- 2026-10-06: README 전체·Python 예제와 최신 공식 인증 문서를 검토한 계획을 학습자가 승인했다. Credentials·middleware 흐름을 그림으로 설명한 뒤 학습자가 같은 요청의401·get_time 실행 로그에서 실행 중단 누락을 진단하고 응답 이후 연결 로직을 조사하자고 답했다. 개념 확인이며 코드 수정·실행 경험은 아직 없고 별도 환경 준비로 진행한다.
- 단원 내용·과제 기준 목표: 요청의 토큰을 검증하는 HTTP MCP Server/Client, JWT 검증, 역할에 따른 권한 제한을 구현하고 성공·거부 원인을 구분한다. 별도 11-simple-auth/practice/·.venv와 기존 SDK2.2 계열을 기준으로 시작 시 버전을 확인한다.
- 환경·다음 실습: 학습자가11 .venv Python3.12.10·MCP2.2.0·인증 API import와 정적 Bearer 서버의 실제 시작 출력을 제출했다. SDK middleware → 직접 TokenVerifier → None/AccessToken 흐름을 그림으로 설명했다. issuer_url의 auth.example.com은 메타데이터용 교육 예시이며 실제 발급 서버·자동 OAuth 연결은 아직 없다. httpx2의 실제 POST로 동일 get_time 요청에 대해 토큰 없음·무효·정상 조건의 상태와 응답을 한 번에 관찰하도록 안내한다. 같은 실행의 서버 도구 로그 확인과 SDK Client 연결을 후속 검사로 둔다.
- HTTP 실행 확인: 학습자가 안내된 세 요청의 없음401·무효401·정상200/isError:false·UTC 시각 결과와 같은 실행의 서버 로그를 제출했다. 없음 요청에는 verifier 로그가 없고, 무효 요청에는 Token rejected·401, 정상 요청에만 Token accepted·get_time executed·200이 남았다. 안내된 실제 HTTP 인증 검사는 완료했으며 전체 독립 인증 구현으로 일반화하지 않는다.
- SDK Client 연결: 별도 sdk_client.py의 httpx2.AsyncClient 기본 Authorization 헤더 → streamable_http_client → Client(mode=2026-07-28) 구조를 그림으로 설명했다. 학습자가 Tools:['get_time']·is_error:false·UTC 시각 결과를 제출해 안내된 인증 SDK Client 실행을 확인했다. 토큰 없는/무효 raw 요청 비교는 반복하지 않는다.
- JWT 시작: 원문 구조·서명 절과 보충 issuer/audience 검증을 구분했다. HS256 키는 발급자/검증 서버만 보유하고 payload는 암호화되지 않는다고 설명했다. 학습자가 정상 서명 만료 토큰은 exp 검사, exp 변조 토큰은 signature 검사로 거부하자고 설명했다. 설명 후 비교 사례이며 독립 구현으로 일반화하지 않는다. issuer/audience·권한의 실제 검증 확인은 남았다.
- JWT 발급: practice/.env의 무작위 키와 issue_token.py의 UTC iat/exp·iss/aud/sub·HS256 발급을 안내했다. 루트 .env는 토큰 행만 교체하며 Client에는 그 파일만 전달한다. 경로가 .practice.env로 전달돼 실패했으나 슬래시/인용부호 명령 후 학습자가 PyJWT2.15.1·저장 완료·mina·만료 시각을 제출해 발급을 확인했다. 키/JWT는 출력하거나 제출하지 않았다.
- JWT 서버 전환: 고정 HS256·issuer·audience·require(iss/aud/sub/iat/exp)와 InvalidTokenError→None, 검증된 AccessToken 정보를 설명했다. 학습자가 SDK 목록/get_time 정상 결과와 두 요청의 JWT accepted:mina·200 및 도구 실행 로그를 제출했다. 실제 정상 JWT 인증은 확인했으며 scopes는 아직 빈 목록이다. Client는 토큰 파일만 읽는다.
- JWT 변조 확인: Client에서 Base64url payload의 sub만 바꾸고 원본 서명과 조합하는 안내된 실습을 수행했다. 학습자가 원본200·get_time 실행, 변조401·InvalidSignatureError·도구 미실행 로그를 제출했다. Client에 키를 주지 않고 encoding과 서명을 구분하는 실제 거부를 확인했다.
- JWT claim 거부 비교: 같은 키로 서명한 expired/wrong-issuer/wrong-audience의 실제 HTTP401과 각각 ExpiredSignatureError/InvalidIssuerError/InvalidAudienceError·도구 미실행 로그를 제출했다. 마지막 정상 토큰 발급도 확인했다. 이전 변조 로그가 포함된 것은 구분한다. argparse는 실험 선택용 보충이며 안내된 검증 실행과 독립 설계/검증 이유 설명은 구분한다.
- RBAC 설명·정책 선택: 검증된 JWT role→서버 scope 정책→HTTP/도구 검사 그림·표를 설명했다. 학습자가 메시지 설정 전용 새 operator에 mcp:access·message:write가 수행에 필요하다고 선택했다. 제공된 scope 의미를 다른 조합에 적용한 범위이며 실제 전체 정책 설계로 일반화하지 않는다.
- RBAC 구현·reader 실행: 안내된 JWT role/ROLE_SCOPES·HTTP required_scopes·get_access_token/require_scope·두 도구를 구현하고 학습자가 reader의 목록 두 도구·get_time 성공·set_message is_error:true를 제출했다. 서버는 세 요청 JWT 검증 후 조회만 실행하고 변경은 Tool denied 뒤 MCP 오류/HTTP200을 반환했다. HTTP 입구403과 도구 내부 오류 결과를 구분하고 목록과 권한을 보충했다. admin/operator는 같은 SDK Client에 역할별 새 토큰을 전달해 비교하도록 안내한다.
- RBAC 역할 비교: admin 두 도구 성공, operator 조회 거부·변경 성공과 실행/거부 로그를 제출했다. visitor는 권한표에 없어 빈 scope이며 JWT accepted 후 HTTP403/insufficient_scope·mcp:access 부족·도구 미실행을 제출했다. reader 복원 명령은 안내했으나 실행 출력은 미확인이다. 실제 서버는 require_scope를 상태 변경 전에 호출한다. 이 순서를 뒤집은 가상 코드의 거부 후 상태 변경 원인·수정 방향을 질문하며 실제 코드를 바꾸지 않는다.
- 진행: 요청 흐름 그림 → 정적 Bearer 토큰과 실제 HTTP 누락/무효/정상 호출 → 로컬 발급 스크립트와 JWT 구조·서명/만료/issuer/audience 검증 → reader/admin의 역할·scope 정책과 도구별 실행 제한 → 실패 비교·현재 MCP OAuth 흐름 개요. JWT의 발급자·검증자·Client를 분리하고 Client에 서명 키를 주지 않는다.
- 교정: 원문 Bearer를 Basic Auth로 부르는 표현, 무효 토큰403, 구형 FastMCP/ClientSession·Logging·session 전제, 실행/미들웨어 이름 오류, Python catch 문법, Client/Server 고정 토큰 불일치, 끊어진 예제 링크를 바로잡아 안내한다. 원문 파일 자체는 이번 계획에서 수정하지 않았다.
- 보강: SDK TokenVerifier/AuthSettings·get_access_token의 검증된 요청 문맥을 활용한다. HTTP 입구의401/403과 MCP 도구 단계의 오류 결과를 구분한다. 실제 HTTP 인증 검사를 in-memory 테스트로 대체하지 않는다. JWT claim 읽기와 검증, 고정 알고리즘·필수 claim·UTC 만료, 역할과 scope 매핑을 먼저 설명하고 변조/만료/다른 issuer·audience 및 권한 부족을 확인한다.
- 범위: 원문의 단순 인증·JWT·RBAC를 중심으로 한다. OAuth2.1·Protected Resource Metadata·PKCE·IdP 연결은 표준 인증과 로컬 교육용 토큰 발급의 차이를 설명하는 개요이며 로그인 서버·refresh/revocation/introspection 구현은 선택 확장이다. JWT만으로 암호화·폐기·자동 갱신이 제공된다고 설명하지 않는다.
- 교수 방식: 새 설명 전에 그림으로 관계를 표현할 수 있는지 판단한다. 인증 흐름·JWT 발급/검증·권한표는 그림/표를 우선하고 코드·실행 결과는 필요한 텍스트로 설명한다. 관련 짧은 항목을 묶고 의미 있는 단계에서 근거를 확인한 후 답변을 기다린다. 보안의 기존 부분 이해 항목은 실제 검증 실습에서 재확인한다.


## 완료 시 추가 근거

- 학습자는 권한 검사 전에 상태를 변경하는 가상 코드에서 먼저 작업했기 때문에 거부돼도 변경이 남는다고 진단했다. 작업 전 권한 검사를 하고 없으면 수행하지 말아야 한다고 수정 방향을 설명했다. 실제 코드는 정상이며 버그를 삽입하거나 수정 실행하지 않았다.
