# Testing & Debugging — 최신 이해 기록

- 학습 근거: [Module 03](../lessons/03-getting-started.md)
- 기준: [RULES.md](../RULES.md). 오류 진단·테스트 선택의 최신 평가를 묶는다. 과거의 보충·집중 질문을 독립 진단 능력으로 일반화하지 않는다.

## 개념별 최신 상태

| 개념 | 상태 | 답변 근거와 확인 방식 | 마지막 확인일 | 후속 확인 |
| --- | --- | --- | --- | --- |
| 응답을 근거로 조사 대상 선택 | 이해 확인 | Inspector의 도구 결과/프로토콜 오류/CLI 안내를 설명한 뒤 새로운 가상 save_note 실패 결과에서 서버 저장 공간과 디스크 공간 부족 메시지를 조사 대상/근거로 제시했다. 다른 가상 로그의 요청 A(multiply 8,4)와 응답 Y(isError:false,31)를 점검해야 하며 기대32와 다르다고 설명했다. 처음 조사 목적이 불명확해 질문했고 작업 성공/결과 정확성 구분을 보충한 뒤 답했다. | 2026-10-06 | 오류 문구와 기대값 불일치에 따른 조사 대상 선택을 확인했다. 실제 장애 검증·복구, 독립 서버 코드/로그 선택, 모든 실패 계층 분류와 id 연결 이유의 명시적 설명은 평가하지 않았다. |
| 서버 로그로 실행과 계산 오류 추적 | 이해 확인 | subtract(50,12)의 로그·반환62로 계산 오류를 판단하고 최종 답변부터 거꾸로 추적한다고 설명했다. stdio 후속 사례에서 예상값 비교→로그 확인을 제시했으며 집중 질문 후 product(4,5)의 예상20과 로그9를 구분해 Tool 구현을 점검한다고 답했다. 종료 코드0을 크래시 없이 실행된 의미로 설명했으며, Inspector에서는 실패로 분류하지 않은 정상 처리이고 정확성 보장은 아니라는 범위를 평가 시 보충했다. 설명·집중 후속 질문을 거친 근거로 독립 전체 진단으로 일반화하지 않는다. | 2026-10-05 | 실제 버그 수정은 미평가이다. 종료 코드0의 계산 정확성 한계는 보충한 범위이며 이후 다른 오류 실습에서 재확인한다. |
| 테스트 사례와 기대 결과 구성 | 이해 확인 | divide의 정상 2·실패 1 요구를 받은 뒤 학습자가 5/2=2.5(일반 흐름), 0/2=0(edge case), 3/0=divide by zero 예외(예상 오류 확인)를 제안했다. 입력·기대값·성공/실패 조건을 구성한 근거이며 기존 divide 경험과 개수 지침을 활용했다. float 0.0 표현과 분자 0 검사 목적의 상세 이유는 평가 시 보충하며 독립 테스트 코드·범위 선택 능력으로 일반화하지 않는다. | 2026-10-05 | 안내된 비교 조건 구현·실패 관찰은 완료했다. 단위/통합 및 수동/자동 선택의 독립 설명은 미확인이다. |
| assert와 기대 예외 검사 | 이해 확인 | 안내한 세 pytest 테스트를 실행하고 /→// 변경의 실패 보고에서 실제2와 기대2.5 불일치를 설명했다. 나머지 통과 이유는 처음에 기대 결과가 같다고 설명해 0 분자의 수치 동등성·0 분모의 계산 전 ToolError 분기를 보충했다. 검사 제거 후에는 기대와 다른 예외가 발생하므로 테스트 실패라고 답했다. 보충 후 새 변경 사례의 설명이며 실제 ZeroDivisionError 명칭은 평가 시 제공했다. / 복구 후 기존 세 테스트 PASSED를 제출했다. | 2026-10-05 | 독립 테스트 작성·전체 범위 선택은 미평가이다. |
| 단위·통합 테스트의 검사 범위 | 이해 확인 | 함수 본문을 유지하고 divide의 @server.tool()만 제거한 가상 변경에서 단위 테스트는 그대로 통과하고 test_registered_tools가 기대한 도구의 서버 등록 여부를 검사해 변경을 발견한다고 답했다. 앞서 직접 함수 검사·in-process Client 범위를 설명한 뒤 다른 변경 사례에 적용했다. 독립 테스트 설계나 전송 계층의 검증 능력으로 일반화하지 않는다. | 2026-10-05 | raw HTTP의 실제 전송 검사와 in-process 범위를 비교한다. 수동/자동 접근 선택의 독립 설명은 미평가이다. |
| 목적에 맞는 테스트 접근 선택 | 부분 이해 | add 계산값의 단위 검사를 추가했지만 방식 선택 이유에는 “그냥요”라고 답했다. 별도 HTTP 앱 연결 실패 사례에서 기존 테스트는 실제 연결을 보장하지 않으며 실제 실행이 필요하다고 설명했으나 구체적 도구 선택은 모르겠다고 했다. HTTP 연결 범위 진단은 맞으며 curl.exe/Inspector HTTP로 실제 요청하는 방법은 평가 시 보충한다. | 2026-10-05 | 다음 실제 연결 진단에서 도구 선택·검사 목적의 이유를 재확인한다. |
| 유한 테스트의 정확성 보장 범위 | 미확인 | add(1,2)==3으로 자연수 합을 보장한다는 설명 뒤 모든 입력 보장 방법을 질문했다. 고정 반환3 반례·유한 테스트와 무한 자연수·1~100 전수 검사 예시·구현 논리 역할을 보충했다. “알겠습니다” 자기 보고만 있으며 전수 검사 실행이나 보장 범위의 독립 설명은 확인하지 않았다. | 2026-10-05 | 다음 테스트 설계에서 검사한 범위와 일반적 정확성 근거를 구분하는지 확인한다. |

## 최종 실행 근거와 한계

- 2026-10-05: 안내된 divide 세 단위 테스트의 통과→임시 // 버그 실패→/ 복구 통과, Client(server)·AnyIO의 네 in-process 통합 테스트를 확인했다. 학습자가 기존 패턴을 참고해 add(1,2)==3을 추가하고 전체 여덟 PASSED를 제출했다. 실제 HTTP 정상 호출은 curl.exe로 확인했다. 실패하는 실제 HTTP 연결의 독립 진단·raw 요청 독립 작성은 미평가이다.
- 2026-10-05 VS Code/stdio·2026-10-06 Inspector의 안내 실행과 가상 로그 진단을 수행했다. 종료 코드0의 정확성 한계는 보충했으며 독립 재확인은 남았다. 실제 버그 수정·전체 장애 복구는 미평가이다.
- 개별 출력·실습 주체·보완 전후는 [실습 근거 보존](../lessons/history/03-implementation-evidence-2026-10-06.md)에 유지한다. 조사 맥락·교정 경위가 필요하면 [Testing 상세](../lessons/history/03-testing-2026-10-05.md), [Inspector 상세](../lessons/history/03-inspector-2026-10-06.md)를 선택한다.
