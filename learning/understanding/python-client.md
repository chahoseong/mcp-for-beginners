## 개념별 최신 상태

| 개념 | 상태 | 답변 근거와 확인 방식 | 마지막 확인일 | 후속 확인 |
| --- | --- | --- | --- | --- |
| tool_call_id와 실행 결과의 연결 | 이해 확인 | 두 get_stock 호출에 stock=8·0 결과를 각각 연결하고 ID는 모델에서 받은 것을 사용한다고 답했다. 예시의 call_A/B 대신 id-1/2로 표현해 실제 ID 보존을 명확히 보충했다. ID만 바꿔 전달하는 후속 사례에서 P17/P18을 0·8로 이해하게 된다고 정확히 진단했다. ID 보충 후 집중 질문의 답변이며 독립 복수 호출 구현까지 평가하지 않는다. | 2026-10-04 | add/subtract 선택 안내 실습은 완료했다. 복수 호출 구현은 별도 확인한다. |
| 모델용 Tool 정의와 입력 schema 보존 | 이해 확인 | required 누락 시 필수 파라미터 정보가 전달되지 않아 모델이 값을 생략할 수 있고 서버 호출은 실패한다고 설명했다. 설명 직후의 진단이다. 이후 안내한 변환에서 integer·required 보존 출력과 모델의 add/subtract 인자를 확인했다. 전체 독립 구현으로 일반화하지 않는다. | 2026-10-04 | 상세 schema 제약·호환성의 독립 처리는 미평가이다. |
| LLM의 Tool 선택·Client 실행·결과 전달 | 이해 확인 | get_stock 사례에서 모델의 요청만으로 조회가 되지 않으며 Application의 MCP 호출·결과 재전달로 최종 답변을 만든다고 설명했다. 흐름 안내 직후의 확인이다. 이후 add와 새 subtract의 선택·실행·최종 답변 출력을 제출해 정상 흐름 실습을 확인했다. 전체 코드·검증 요청은 안내했으며 독립 구현 또는 오류 경로 적용까지 평가하지 않는다. | 2026-10-04 | 실패 결과 재전달·추가 호출 반복의 실제 처리는 미평가이다. |
| await와 순차 실행 | 이해 확인 | 두 await 호출의 코드에 첫 호출→first 저장→둘째 호출→second 저장→print 순서를 직접 표시했다. 요청·응답 수신의 내부 구분은 에이전트가 평가 시 보충했다. 직전 설명의 실행 순서 확인이며 독립 병렬 처리 설계의 증거는 아니다. | 2026-10-02 | 안내된 실제 Client 호출은 수행했다. 병렬 실행 구현은 미평가이다. |
| Task 등록과 await 중 다른 작업 실행 | 이해 확인 | 단일 Task 예제 설명 후, 두 Task를 먼저 등록하고 report_task를 먼저 await하는 코드에서 send_notice가 먼저 완료될 수 있고 보고서 대기 중에도 실행된다고 자신의 말로 설명했다. 답변 뒤 create_task는 실행 등록이라는 용어를 보충했다. 설명 직후 두 Task 사례의 추론이며 실제 동시성 구현/취소 능력으로 일반화하지 않는다. | 2026-10-12 | 실제 동시성 구현은 미평가이며 취소/정리 판단의 최신 근거는 같은 파일의 해당 항목을 따른다. |
| async with의 연결 관리·asyncio.run | 미확인 | 연결 준비·정리와 event loop 실행을 설명했으나 독립 답변 근거는 없다. | 2026-10-02 | 연결 코드 수정·실행 시 필요한 범위에서 확인한다. |
| AnyIO 취소 중 await 정리 보호 | 이해 확인 | 제한된 shield 설명 후 전체 처리까지 보호한 코드에서 자체 기한 만료 시 await 정리가 완료되지 못할 수 있다고 진단했고 교사 실행으로 확인했다. 기한 전 외부 취소를 묻는 집중 후속 질문에서는 process_work도 보호 범위 안이므로 중단되지 않는다고 설명했다. 같은 날짜의 부분 이해는 외부 취소 근거 미확인 상태였으며 후속 답변으로 보완했다. 설명/집중 질문 뒤의 범위 판단이고 실제 SDK async 정리 독립 구현은 미평가다. | 2026-10-12 | 자체 기한과 외부 취소의 보호 범위 구분은 확인했다. 보호된 정리의 실제 완료 검증·운영 정책 구현은 별도 근거가 필요하다. |
| 취소 예외와 정리 코드의 제어 흐름 | 적용 확인 | Task.cancel/CancelledError/finally 예제 설명 후, 파일 수신 await의 취소 예외가 뒤의 file.close를 건너뛰고 호출 측으로 전달됨을 설명했다. 정리 누락 코드에 try/finally를 직접 적용해 file.close를 finally로 이동했다. 교사가 제출 함수 그대로 정상 완료/취소를 실행해 두 경우 file.closed=True와 취소 예외 전파를 확인했다. 문서/이전 예제 참고 허용의 작은 적용이며 전체 자원 설계/실제 MCP 취소 구현으로 일반화하지 않는다. 이전 이해 확인(같은 날짜)은 제어 흐름 설명 범위였다. | 2026-10-12 | 주어진 파일 열림 성공 조건의 수정은 확인했다. open 실패 시 미할당 변수를 참조할 수 있어 파일 획득을 try 앞에 두는 교사 보강을 제공한다. 새로운 숨은 채점 조건으로 사용하지 않으며 await 정리 보호·MCP 취소 전파는 아직 미평가이다. |
| 실패 결과와 예외의 Client 처리 | 이해 확인 | get_weather 사례에서 except만 있는 코드는 성공 문구를 출력하며 result.is_error를 검사해야 한다고 설명했다. 직접 작성한 응용 메서드에 is_error 분기를 넣었고, 지적 후 Tool·Resource 두 요청을 하나의 try로 감싸도록 수정했다. 보완 후 코드 확인이며 예외 범위의 독립 적용으로 일반화하지 않는다. | 2026-10-04 | 새 사례의 독립 예외 처리와 종료 코드·기능 정확성 구분은 아직 평가하지 않았다. |

## 최종 실행 근거와 한계

- 2026-10-02~04 Client: 최신 Client 연결·Tool 목록/호출·Resource 템플릿/읽기·오류 두 경로를 안내에 따라 실행했다. run_custom_requests의 정상값 비교·Resource 읽기·is_error 분기를 작성했으며, 지적 후 두 요청을 공통 try로 감쌌다. 파일과 에이전트 재실행의 True·Hello, Mina!로 최종 보완을 확인했다. 안내 코드·입력과 피드백을 활용한 완료이며 독립 예외 처리 능력의 증거로 일반화하지 않는다.
- 2026-10-04 LLM Client: add(20,2)→22 정상 흐름을 확인했다. 학습자가 새 subtract 함수를 작성했고 안내한 선택 검증으로 subtract(141,20)→121·add(141,20)→161과 최종 답변을 제출했다. tool_call_id 이해의 보충 여부는 위 평가를 따른다. 실패 결과 재전달·복수/반복 호출 구현은 미평가이다.
- 개별 출력·보완 전후·안내 여부는 [실습 근거 보존](../lessons/history/03-implementation-evidence-2026-10-06.md), 전체 LLM 교정 경위는 [LLM Client 상세](../lessons/history/03-llm-client-2026-10-04.md)에 보존했다.
- 로그·종료 코드·Inspector 진단과 테스트 평가의 최신 상태는 [Testing & Debugging](testing-and-debugging.md)에 있다. Resource 발견/읽기의 최신 상태는 [Tools, Resources, Prompts](tools-resources-prompts.md)에 있다.
